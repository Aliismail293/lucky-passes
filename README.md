# lucky-passes

**How often do answer-only scores overstate retrieval-augmented generation (RAG)?**

A *lucky pass* is a RAG answer that is judged correct even though no gold passage was retrieved.
The model got it right from memory, by guessing, or from a passage the gold labels don't know about, and an
answer-only score gives the retriever the credit.

This repo measures lucky passes per question across datasets, retrievers, k and model sizes, using small
local models (Ollama). It reuses [ragaudit](https://github.com/Aliismail293/rag-tester) to generate and verify
questions for corpora that have none.

| | Answer correct | Answer wrong |
|---|---|---|
| **Gold retrieved** | True pass | Grounding failure |
| **Gold not retrieved** | **Lucky pass** | Miss |

**Overstatement = answer accuracy − true-pass rate = lucky-pass rate.**

## Reproduce in 3 commands

You need [uv](https://docs.astral.sh/uv/) and [Ollama](https://ollama.com) with the models in `configs/`.

```
uv sync
uv run python scripts/download_data.py
bash scripts/overnight.sh pilot
```

`bash scripts/overnight.sh full` runs the core grid and the k-sweep. Any run can be stopped and restarted:
every model call is cached in `data/cache/calls.sqlite`.

No Ollama? `uv run python scripts/run_pilot.py --mock` runs the whole pipeline on toy data with a fake model.

## Results

The full run is in `results/core/` and `results/ksweep/`. Plain-words findings, with intervals and n, are in
[`results/FINDINGS.md`](results/FINDINGS.md). They are not yet checked against human labels (the audit is pending).
In short:

- **HotpotQA and NQ: lucky passes are rare** (at most 1.3% per cell, n = 150), mainly because retrieval rarely
  misses every gold passage. When it does miss, the answer is still right about 7–11% of the time.
- **A university course calendar: 13–25%**, but mostly because the answer was in a retrieved passage that wasn't
  labelled gold (boilerplate fields shared by many course entries). Only 3–6% had the answer nowhere in the
  retrieved text.

## Checking your own RAG app for lucky passes

Each check needs only what a RAG evaluation already logs: per question, the retrieved passage ids and texts, the
gold passage ids, the gold answer(s), and the correct/incorrect verdict.

1. **Bound it.** The lucky-pass rate can't exceed the share of questions with no gold passage retrieved. If hit@k
   (any gold) is 97%, answer-only accuracy overstates retrieval by at most 3 points.
2. **Count lucky passes.** These are correct answers with no gold passage in the top k.
3. **Check your gold labels before believing them.** For each lucky pass, test whether a retrieved non-gold passage
   contains the gold answer (`scripts/extra_analyses.py`, `answer_in_context`). If most do, your gold labels are
   incomplete; that's a labelling problem, not luck. Answers that occur in many passages ("In Class", "Science")
   are the usual cause (`scripts/utm_sensitivity.py`).
4. **Ask the model closed-book** for the lucky passes that remain. Correct closed-book means memory. Wrong means
   guessing or a judge error, so read a few by hand.

To run this repo's own pipeline on your corpus, put your documents in a folder and point `LP_UTM_CORPUS` at it:
questions and single-chunk gold labels are generated by ragaudit, and step 3 is especially important for them.

## Layout

| Path | What it does |
|---|---|
| `lp/datasets.py` | Loads HotpotQA, NQ (BEIR + NQ-open), and ragaudit-generated questions for the invented and UTM corpora |
| `lp/retrieve.py` | BM25, dense (nomic-embed-text), hybrid (reciprocal rank fusion) |
| `lp/generate.py` | Closed-book, RAG and oracle prompts |
| `lp/judge.py` | Contains-match plus a cross-family LLM judge, and their agreement |
| `lp/classify.py` | True pass / lucky pass / grounding failure / miss; memory vs guess lucky |
| `lp/cache.py` | Hash-keyed SQLite cache of every model call |
| `lp/stats.py` | Bootstrap CIs, exact (Clopper-Pearson) intervals, paired bootstrap, exact McNemar, Holm |
| `lp/report.py` | summary.json, tables (CSV + LaTeX), figures (PNG + PDF), run report |
| `lp/runner.py` | Runs a config end to end, with the time estimate and the 10-hour gate |
| `scripts/` | download, preflight, run_pilot / run_core / run_ksweep, overnight.sh, make_paper_assets, check_numbers |
| `scripts/compare_conditions.py`, `extra_analyses.py`, `utm_sensitivity.py` | Paired tests and post-review analyses, from the committed records (no model calls) |
